## FEATURE: DOCUMENTS (Working Papers + Draft Resolutions)

### Chair view (DocumentsModal)
- Two tabs: Working Papers | Draft Resolutions. **Vote** (`documents_vote_btn`, Moderator only) is a small gold 64px tile at the end of the "+ Submit new ..." row (17 Sep 2026, owner): a big `Vote` icon with the word small beneath (the icon-button rule, CLAUDE.md §8). It opens `/voting/[code]?chairName=...` only when a draft resolution is `introduced`, `passed` or `failed` (the voting picker's own filter); otherwise it opens nothing and shows a small forest note above the button through `Portal` (`documents_no_dr_title` / `documents_no_dr_body`, the DR name from `docName`, `role="status"`, z 70 over the dialog), which closes after 3.6 s, on a press elsewhere, or on Escape (captured, so the Documents dialog stays open). It is the ONLY way to the voting page from the modal: the full-width GO TO VOTING banner on the DR tab was removed on 16 Sep 2026 (owner's instruction), with its key `documents_go_to_voting`. The voting page chooses the draft resolution and runs the roll call.
- Each doc has status: submitted → on-floor → introduced → passed/failed
- Status and approval render as ONE pill set (`Pill`, `STATUS_PILL`, `APPROVAL_PILL` in `DocumentsModal.tsx`): Lucide icon + label, tinted fill with an inset-shadow ring, no border. Submitted = neutral ink (FileText), On floor = forest tint (CircleDot), Introduced = gold (Presentation), Passed = solid forest with gold text (Check), Failed = muted red (X); Approved / Rejected are outline-only (BadgeCheck / Ban). Every text colour is AA on its fill.
- "Introduce" button starts a presentation flow: setup timers → reading → presentation → Q&A → auto-pass (WP) / back to the list (DR)
- WP auto-passes after Q&A. DR goes to /voting/[code] page. The old in-modal `DocumentVote` screen and stage `'vote'` were dead code and are gone.
- **The introduction screen is document-first** (16 Sep 2026). The paper fills the screen (`IntroDocument`: a PDF through `PdfViewer`, or the text on a page card); the intro bar has the code chip (14.5px) and title (17px), the stage switcher with **Finish** beside it, zoom (text paper only; a PDF has its own toolbar) and the Timer button when hidden. The stage clock is a floating timer, `StageTimerDevice`.
- **There is no close X on a stage screen** (17 Sep 2026, owner: "in the draft resolution introductions and presentations, remove the X in the top right corner. The only way out is either clicking Finish or the next arrows"). A presentation is left in exactly three ways, all deliberate: **Finish** (asks first while time is left), **Continue / next** out of the last timed stage (both `finishIntroduction`: a WP passes, a DR stays `introduced`), or the timer's **Timings** key back to the order of proceedings, whose round Back key (`documents_setup_back`) returns to the documents list. The timer's previous-stage key at the FIRST timed stage lands on that same setup screen, so a chair is never trapped: from any stage, two presses reach the list. **Escape never leaves a stage** (it only folds an open Finish question); on the SETUP screen it still leaves, as the keyboard twin of the Back key, because nothing has been written there yet. Verified 17 Sep 2026 (1280x800 and 1024x640): no button with a close label anywhere in `[data-doc-intro]` on either screen; Escape on a stage left the introduction standing; Finish → Finish now returned to the list with the DR `introduced`; Timings → Back returned to the list.
- **The chair's top bar stays usable during an introduction (17 Sep 2026, owner: "still have the settings, chat, scoreboard and join code option").** Both introduction screens (setup and every timed stage) render through `introFrame` in `DocumentsModal`: a Portal at `z-45`, with a 44px strip (`CHAIR_TOP_BAR_H`, the bar's own ivory) under the chair page's header. `DocumentsModal` reports `onIntroChange(active)` (false on unmount too); the chair page keeps `docIntroActive` and, while it is true, gives the header `relative z-[46]` and replaces its Roll Call / Motions / Documents tabs with an empty spacer. The GavelChip, session code (presenter), Chat, Scoreboard and Settings are the SAME buttons and dialogs as on the floor. Layering: intro 45 < header 46 < every GrowDialog (50) < GavelChip menu (60) < code presenter (400, on body); the timer device is `zIndex 20` inside the intro's own stacking context, so dialogs always cover it. The sidebar stays mounted under the intro. Do not raise the intro to 50 or the header past 49. Verified 17 Sep 2026 (1280x800, 1920x1080): Settings, Scoreboard and Chat each opened over the intro and closed back to it with the paper, stage and clock untouched; the presenter opened; after the WP passed the tabs came back and the header lost its z-index.
- **Stage switcher** (17 Sep 2026, `src/components/documents/StageSwitcher.tsx`, replaces the stage chips): a segmented control centred in the intro bar (grid `1fr auto 1fr`). Each segment: number (a check once that stage was finished with Next / Continue, `doneStages` in the modal, reset on a new introduction and on confirming new timings), name (`documents_switch_*`), minutes; the current one is a forest thumb that slides (240 ms, none under reduced motion) with `aria-current="step"`; a 0-minute stage is dimmed, struck through, `aria-disabled`, shows `documents_setup_skipped` and cannot be chosen. Click / Enter / Space jumps (`jumpToStage` → `enterStage`: a fresh paused clock, exactly like Next and Back, nothing written, the paper untouched); Arrow keys move focus between selectable segments (mirrored in RTL), Home / End. The switcher has no Timings button any more: the way back to the order of proceedings is an icon-only key in the timer device's header (below).
- **Finish** (17 Sep 2026, owner: "a button next to the stage indicators to finish the presentation"): a gold tile right of the switcher, a big `CheckCheck` icon over the small word `documents_finish` (label / tooltip `documents_finish_title`). `handleFinish` calls the same `finishIntroduction` as Continue out of the last stage (WP → `passed`, DR stays `introduced`, `introState: null`, one checked write, flow closed). While the current clock has time left (`introRemainingNow(clock, serverNow())`) or a timed stage is still ahead, it first opens a small question under the button (`documents_finish_confirm`, the outcome `documents_finish_outcome_wp` / `_dr`, **Finish now** focused, **Keep going**); Escape folds it, and changing stage, Timings or closing clears it. The intro bar is `relative z-30` so the question sits over the timer device (z 20). Verified: Q&A then Reading via the switcher and the arrow keys kept the same PDF scroller node at `scrollTop` 900.
- **Papers render through pdf.js, not the browser iframe (17 Sep 2026, owner: "a more native design, mymun does it").** `pdfjs-dist` (pinned 6.3.289). `src/components/documents/pdfLoader.ts` imports it lazily in the browser only, serves the worker from our origin (`new Worker(new URL('pdfjs-dist/build/pdf.worker.min.mjs', import.meta.url), {type:'module'})`, works under Turbopack), and caches loaded documents by URL (LRU of 8) so a card thumbnail, the card viewer and the introduction parse a file once. `src/components/documents/PdfViewer.tsx`:
  - continuous vertical pages on the `#E4DCCA` ground, soft forest shadows, and ONE slim forest pill toolbar floating over the top: previous / next page, a page field ("n of N", Enter jumps), zoom out / percentage (actual size) / zoom in, Fit width (gold when on), open the original (plain link), download (the bytes pdf.js already holds, as a blob, so it works cross-origin). Ctrl / cmd + wheel (trackpad pinch) steps the zoom.
  - zoom is `'fit' | number` (steps 50% to 300%, 100% = 96/72 CSS px per point), a PROP owned by the caller. Fit width is capped at 1200 CSS px of page.
  - lazy: an IntersectionObserver (root = the scroller, one screen of margin) keeps a canvas only on near pages and gives far ones back; canvases are drawn at devicePixelRatio x the FitToScreen scale (capped at 16M px per page); on zoom the old canvas stretches and is redrawn 140 ms after the last step, swapped in only when finished, so nothing flashes blank. Verified: 8-page paper, 2 of 8 canvases alive, a 1200px page drawn 2341px wide at dpr 2.
  - a zoom keeps the reader's place (page + fraction remembered on scroll, restored in a layout effect).
  - ANY pdf.js failure (worker, CORS, broken file) falls back to the old iframe with the transform zoom. `PdfThumb` draws page one for the card's left strip (lazy), falling back to a FileText icon. The card's inline viewer is a compact `PdfViewer` (480px, its own local zoom).
  - the introduction zoom is remembered in `localStorage gavelling-intro-zoom` (`fit` or a step; default `fit`).

The seven-segment LCD, gold keys, bezel, lamps and blink are gone.
  - **Nothing is clipped, by measurement.** Hidden 100px rulers (the digits "88:88" and all four primary labels, re-measured by a ResizeObserver when fonts load) give real widths. The keys try, in order: all four with the label; without previous stage; without reset; without next; then the primary as an icon with next; then the icon alone. A layout is taken only if it fits (in a row, only if the digits keep at least min(row height, 26px)). The digits are sized to the space left (stacked: capped at 220px). Checked at 176x64, 220x64, 300x80, 420x90, 176x200, 200x150, 260x120, 320x204, 480x300, 700x420, 240x240 with "Resume" and at 230x70 with "Continue": no key, label or digit outside its box.   - resizable on BOTH axes from all four edges and corners, minimum 176x64. A box under 124px high (or very wide and under 170px) is one row (clock | keys, the bar along the bottom edge); taller it stacks (header, clock, bar, keys). Radius = key radius + padding (concentric). Default 320x204, lower inline-end corner.
  - moved by dragging the card anywhere but a key; window pointer listeners, deltas divided by the `#fit-root` scale, clamped on screen on every move, resize and window resize. Keyboard: Arrow keys on the focused header label move it, on the focused corner grip resize it (16px, Shift 64px).
  - the box is remembered per device in `localStorage gavelling-intro-timer-device` `{x,y,w,h}`. Hiding (`documents_timer_hide`) and the intro-bar Timer button are unchanged; hiding never pauses the clock.

### The introduction (Resume / Pass / Fail removed, 15 Sep 2026)
- **There is no Resume, Pass or Fail on a card any more** (removed at Peter's instruction). A card offers Introduce (submitted / on floor, after approval when the gate is on), and nothing else for the flow. A WP whose introduction was closed before it finished is still `introduced` and its card offers **Introduce** again (setup prefilled with the saved times), so it can always reach its automatic pass. An introduced DR shows no flow button: it is decided on the voting page.
- The stage lives only in modal state now. `documents.intro_state` is no longer written except back to `null` (on confirming the timings, finishing, and skipping), which also clears stages left by the retired Resume flow. The column, `DocIntroState` and `parseIntroState` stay so existing rows still load; nothing reads a persisted stage.
- The on-screen stage clock is still **anchor-based**: remaining = `base - (serverNow() - startedAt)` via `introRemainingNow` (`src/lib/documentFlow.ts`), stamped with `serverNowIso()` (RULE 6b), `startedAt` null = paused. `StageTimerDevice` only refreshes a local `now` (500 ms interval, inside the device, only while running). Nothing is written per second, and dragging, resizing, zooming and hiding write nothing at all (RULES 3 to 5).
- Confirming the timings writes timings + `status` (`introduced`, or `passed` for a WP with every timer at 0) in ONE update.
- Back skips 0-minute stages and lands on setup; a stage with a 0-minute timer renders as complete (Continue), never a blank screen.
- Every flow write is optimistic first and then checked; a failure shows `documents_intro_save_failed`. Delete is checked too and puts the card back on failure.

### Commenters, delete, codes, failed submissions (D-10, V-6)
- `DocCard` receives `isViewOnly`: a Commenter gets no approve / reject / introduce / Vote / delete (UI gate only, RULE 15).
- Delete asks first (inline "Delete this paper?" Delete / Keep).
- **Document codes are assigned by the database.** BEFORE INSERT trigger `documents_assign_doc_code` computes `WP 1.n` / `DR 1/n` per committee under a per-(committee, type) advisory lock (n = max(count, highest trailing number) + 1). The client `docCode` is a preview and is ignored; two simultaneous submissions can no longer collide.
- Both submit paths (chair `SubmitForm`, delegate submit tab) check the `addDocument` result: on failure the form stays filled and `documents_submit_failed` is shown.

### Delegate view
- "View Documents" tab: shows ALL docs (WPs + DRs) with status badges
- "Submit Documents" tab: submit form only (no list of existing docs shown)
- PDF rows resizable by dragging right edge

### Document names are renameable (Settings → Motions → Documents)
- `CommitteeSettings.documentNames` holds singular + plural for both types; defaults are the English `DEFAULT_DOCUMENT_NAMES`.
- Mirrored into `committees.settings` JSONB by the SettingsPanel `upd` helper, so delegates on other devices see the rename.
- **Every** user-facing render of the type name goes through `docName(committee, type, form, translatedFallback)` in `src/lib/docNames.ts`. Never hardcode "Working Paper" / "Draft Resolution" in UI text again.
- Renaming is presentation only — `DocumentType`, the `documents.type` column and the `'working-paper'` / `'draft-resolution'` discriminators never change.

### Document approval gate (Settings → Motions → Documents)
- `requireDocApproval` (default false). Read from the committee ROW via `requireDocApproval(committee)` in `src/lib/documentFlow.ts` (never the local store, so another chair's toggle applies); when on, each doc card gets an approve/reject control and `CommitteeDocument.approval` gates introduction. The gate covers re-introducing an already introduced working paper too (a rejected or never-approved introduced WP shows Approve / Reject instead of Introduce), so a rejection can never be walked around by reopening an introduction.
- **`documents.approval` did not exist until 14 Sep 2026** (migration `documents_intro_state_and_approval`). Every approve/reject before that was rejected by PostgREST and only logged, so with the gate on no paper could ever be introduced.

### Document limits — LEGACY, NO UI
- `wpSubmissionLimit` / `drSubmissionLimit` still exist on `CommitteeSettings` and are still ENFORCED on submit (`DocumentsModal.tsx:469`), but **nothing writes them** — the Settings UI and the `onResetDocuments` Reset button no longer exist anywhere in `src/`.
- In practice they are always `null` (unlimited) unless an old committee row still carries a value in its settings JSONB.
