## FEATURE: GSL (General Speakers List)

### How it works
- Delegates are added to speakersList via AddSpeakerInput (chair) or GSL Request (delegate → chair approves)
- Chair clicks "Start" to begin timer for currentSpeaker
- Chair clicks "Next" to advance: currentSpeaker logs speaking time, next delegate from speakersList becomes currentSpeaker, speakersList shrinks by 1
- Timer is isolated to speakerTimeRemaining atom
- Progress bar shows time progress

### Rules
- currentSpeaker can NEVER be re-added to speakersList
- If delegate goes absent, remove them from speakersList AND caucusQueue (but NOT during pre-session roll call)
- GSL is NEVER wiped when entering a caucus
- **An interrupted speaker keeps their GSL place (18 Oct 2026).** A seated delegation is no longer a `speakers_list` row (RULE 2: Next and Start on deck delete it), so a caucus accepted, a Suspend passed or an organiser pause over a seated GSL speaker used to drop them from the GSL for good (owner: "if a delegate is on the GSL, a motion gets started and they return back to the GSL, they might disappear ... The GSL should stay absolutely the same, even if they have time remaining"). Now they go back to the FRONT of the GSL (`src/lib/gslFloorReturn.ts`, see motions-modal.md) and are on deck when the room returns to it.
- **The GSL may always elapse (17 Sep 2026).** `gslRequireNextSpeaker` has NO effect on the floor any more (owner): the chair page never reads it, `isLastGSLSpeaker` and the `gsl_never_empty_warning` strip are gone, Start is blocked only below quorum, and Finish is always offered on the last speaker. The field stays on `CommitteeSettings` (default false) and in old rows' settings JSONB so they still load; Settings has no row for it.
- **Finish (G-1).** When the GSL behind the current speaker is empty, the Next button is replaced by **Finish** (`gsl_yield`, Moderator only, hidden when ended). `handleYieldFloor` logs the speech through `logFloorSpeech` (`src/lib/floorSpeech.ts`, the one speech logger, see RULE 6b) and clears the floor exactly like Next with nobody queued.
- **Item 6 guard (Oct 2026).** When a moderated caucus ends (often by expiry, with nobody pressing anything) the sidebar and the top strip swap from the caucus queue to the GSL under the chair's pointer, and a press meant for a caucus row used to delete the same delegation's GSL place. `handleRemoveFromSpeakersList` ignores presses for `LIST_SWAP_GUARD_MS` (1.5 s) after a moderated caucus ends. See RULE 4 for `gslDedupeApplies`, the other half of "GSL speaker removed after the mod".
- **Auto start (Oct 2026, Settings → Access → Speaker clock, `autoStartSpeakerTimer`, default false).** Next (GSL), caucus Next and a Tour de Table advance seat the next speaker WITH the clock running: `handleNextSpeaker` and `handleNextCaucusSpeaker` use ONE `serverNowIso()` stamp as both `seated_at` and `started_at` in the same single `nextSpeakerInDB` update (like `handleStartOnDeck`), and in a caucus the total is re-anchored running from the same stamp in the same caucus write. Read at PRESS time (`autoStartOn()`) from the store, which follows the row (`dbAutoStart`), never below quorum, suspended or ended (the clock then stays paused as before). A fresh seat bumps the gavel knock's anchor epoch, so an auto-started clock never knocks on the jump. A Room Order placeholder's current_speaker write fails as always (uuid column); its clocks still run locally and in the caucus JSONB.
- **Yield (Oct 2026, item 18, `src/components/YieldPopover.tsx`).** A Yield key in the GSL speaker controls (`yieldControl` on `SpeakerControls`, a soft sage tone, `speaker_ctl_yield*`; drawn unavailable with `speaker_ctl_need_speaker` or `speaker_ctl_yield_no_time`) opens a movable `DraggablePopover` (z 40 / 41, the third floor panel beside Add time and RTR, `FloorPopover` `'yield'`, closed with the others on `floorCloseKey`). Moderator, GSL, a seated speaker with time left, not ended or suspended (`canYieldNow`). The speaker gives away their REMAINING time, never more:
  - **Next speaker** (`handleYieldToNext`): the next GSL delegation is seated through `handleNextSpeaker({ yieldBonus, run })` with `speakerTimeLimit + remaining` as the slot, so `time_granted` starts at the extended slot (T-3) in the same single current_speaker write; the clock runs on if it was running (or by auto start), never below quorum. The yielder's speech is logged by Next as usual.
  - **Another delegation** (`handleYieldToOther(country)`): pause at the live value in one write, then `handleYieldFloor` (exactly like Finish: logs the speech, clears the floor, the next GSL delegation goes on deck), and the panel times the recipient LOCALLY for exactly the remaining seconds, like Right of Reply (Start / Pause / Done, no extra time, nothing written per second, device-clock anchor in the component's own state, its own gavel-knock anchor).   - Known limit: Restart after a yield to the next speaker reseats the plain speaker time limit; the yielded seconds are not kept by Restart.
  - Both write ONE `yield` ledger row through `logYield` (`floorSpeech.ts`): `{country: from, type: 'yield', to, seconds, mode: 'next' | 'other', context: 'speakers-list'}`, idempotent by `yieldTurnKey` (the yielder's own turn key + `|yield`). It scores nothing. History draws it with the `Forward` icon as `sb_hist_yield` ("yielded 0:42 to Brazil"); the record export labels it Yield.

### DB operations
- `addToSpeakersList(…, at = 'end' | 'start')` / `addToCaucusList(…)` — call the `speakers_list_add` RPC (migration `speakers_list_atomic_append_and_reorder`, 14 Sep 2026), which assigns `max(position)+1` (or `min-1` for "add first") under a per-(committee, list_type) advisory lock. **NEVER pass a client-computed position** (`queue.length + 1`, `Date.now()`, `0`): after a Next or a removal leaves a gap, `length + 1` lands on an existing row, and two rows with one position have no defined order, so the queue reshuffled on every refetch (production evidence: QKUHGA caucus queue, two rows at 4 and two at 5). The RPC is SECURITY INVOKER, so the unchanged `speakers_list` RLS still gates it; it is idempotent on the (committee, delegate, list_type) unique key.
- Every queue read orders by `position, created_at, id` (`getCommitteeByCode`, `getSpeakersLists`). Keep all three keys so devices agree even on legacy tied rows.
- `removeFromSpeakersList` — deletes from speakers_list where list_type='gsl'
- `reorderSpeakersList` — ONE `speakers_list_reorder` RPC call: a single in-place UPDATE under the same list lock, listed rows get 1..n and rows the caller did not know about follow in their existing order, so no two rows can share a position. Calls are chained per list on the client, on the SAME chain as `addToSpeakersList` / `addToCaucusList`, so two quick drags reach the server in order and a drag right after an add never runs before the insert. The chain (`chained()` in `committeeService.ts`) catches and logs, so fire-and-forget callers never get an unhandled rejection. (NOT delete + reinsert: a DELETE realtime event flashes an empty list on delegate phones. NOT N parallel single-row updates either: interleaved drags produced duplicate positions and a refetch mid-batch read a half-applied order.)
- `nextSpeaker` — updates current_speaker row, optionally removes a delegate from speakers_list
- `startSpeakerTimer` — writes started_at AND time_remaining together (one anchor)
- `pauseSpeakerTimer` — writes `{ started_at: null, time_remaining: live }` in one update (the pause; see RULE 6b)
- `stopSpeakerTimer` — clears started_at only; used where the next write seats a fresh clock anyway (ending a caucus with nobody on the floor). Not for a pause, not for a restart
